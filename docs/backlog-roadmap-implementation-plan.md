# План реализации task.rtfd: дорожная карта и отдельный бэклог

Реализация выполнена 31.10.2026. Итоговая модель и правила описаны также в `architecture.md` и `planning-workbench-overview.md`. Разделы ниже сохраняют обоснование решений и критерии проверки.

По результатам последующего ревью исправлены все замечания F1–F6 из `backlog-roadmap-implementation-review.md`, добавлены регрессионные проверки. Изменения схемы объединены в одну миграцию 22; проверены обновление прежней базы, чистая установка и откат при ошибке.

## Цель и границы

Текущую страницу «Бэклог» переименовать в «Дорожная карта», добавить отдельный полноценный бэклог для будущих задач и связать его с существующим «Планированием». В подсказках назначения релиза показывать даты ПРОМ не раньше текущей даты; в подсказках фильтра — даты ПРОМ из выбранных кварталов. В обоих местах всегда разрешать ручной ввод валидной даты вне подсказок. Старые статусы заменить: `notdone → canceled`, `partial → done`. Сохранить неактивных участников в существующих задачах и запретить их новые назначения. Алгоритм автораспределения, его приоритеты, ограничения и расчёт распределения не менять.

Основание: текст и четыре изображения из `task.rtfd`, текущая реализация frontend и backend.

## Что уже есть в проекте

- `src/views/BacklogPage.tsx` — текущая страница задач: фильтры, сортировка, создание, копирование, участники, нагрузки, история и Jira.
- `src/components/BacklogTaskCard.tsx` — общая карточка; она используется также на review-странице планирования.
- `tasks` / `TaskEntity` — реальные задачи. Сейчас отдельного признака принадлежности к странице нет.
- `planning_backlog_items` / `PlanningBacklogItemEntity` — отдельные заготовки для планирования. Задачи со статусом `backlog` из `tasks` туда автоматически не попадают.
- `PlanningWorkbenchService.apply()` сейчас создаёт новые реальные задачи и удаляет применённые заготовки. Явного переноса существующей задачи в planning backlog нет.
- При расчёте занятой ёмкости `TaskAllocationRepository` исключает только статус `backlog`. После разделения страниц этого недостаточно: отменённая задача нового бэклога тоже должна оставаться вне занятой ёмкости.
- В `uiSlice.ts` хранится один набор настроек бэклога; в `BacklogPage.tsx` общий список релизов используется и для фильтра, и для назначения релиза.

## Предлагаемые правила

### Принадлежность к странице

Добавить в реальную задачу `workspace: ROADMAP | BACKLOG`. Хранить оба списка в существующей таблице `tasks`, сохраняя общий набор атрибутов и операций.

Отдельный признак необходим, поскольку «Отменена» допустима на обеих страницах. При отмене сохранять текущий `workspace`.

| Действие | Статус результата | Страница результата |
| --- | --- | --- |
| Создать или скопировать задачу на дорожной карте | `inprogress` | Дорожная карта |
| Создать или скопировать задачу в бэклоге | `backlog` | Бэклог |
| Выбрать «В бэклоге» в существующей задаче | `backlog` | Бэклог |
| Выбрать «В работе» | `inprogress` | Дорожная карта |
| Выбрать «Выполнено» | `done` | Дорожная карта |
| Выбрать «Отменена» | `canceled` | Текущая страница |

Перемещение между страницами выполняется обновлением той же записи: ID, история, участники, заметки, релиз и нагрузки сохраняются.

В фильтре дорожной карты оставить «В работе», «Выполнено», «Отменена». В фильтре нового бэклога — «В бэклоге», «Отменена». Выбор статуса в карточке должен позволять переходы из таблицы выше.

### Совместимость старых данных

Предлагается перенести существующие `backlog` в `BACKLOG`, остальные задачи — в `ROADMAP`; существующие отменённые задачи останутся на дорожной карте, поскольку определить их прежнее происхождение невозможно.

Пользователь зафиксировал замену статусов: `notdone → canceled` («Отменена»), `partial → done` («Выполнено»). Выполнить SQL-миграцию действующих задач; удалить старые значения из рабочих типов, списков UI и допустимых значений API. В БД ограничить множество статусов четырьмя значениями: `backlog`, `inprogress`, `done`, `canceled`.

Сохранённые UI-фильтры преобразовать по той же таблице с удалением дублей. Для сохранённых preview/review выполнить версионирование формата и нормализацию старых статусов или сброс несовместимого черновика с объяснением. Старые значения в журнале истории являются фактами прошлых событий: журнал массово не переписывать, отображение исторических значений обрабатывать общим форматтером. Поставлять frontend и backend согласованно, чтобы старый UI не возвращал удалённые статусы.

### Связь с планированием — рабочее допущение

По результатам ревью рекомендуется сохранять исходную задачу в бэклоге до применения плана, а после применения обновлять её с тем же ID и переводить на дорожную карту. Это рекомендация, а не отдельно подтверждённое пользователем поведение. Так сохраняются история и Jira-связи и не возникает второй реальной задачи с той же оценкой.

При варианте с независимой копией вместо связи и обновления исходника использовать существующее создание задачи в `apply`; отдельно определить дальнейшую судьбу исходной задачи, чтобы она не выглядела незапланированной повторно.

## Этап 1. Данные и серверные правила

1. Добавить новый Liquibase changeset и подключить его в `server/database/changelog.yml`:
   - замена `notdone → canceled`, `partial → done` и ограничение допустимых статусов;
   - поле `tasks.workspace`, заполнение существующих строк по правилам выше;
   - `NOT NULL` и ограничение допустимых значений;
   - индекс для выборки команды и страницы с учётом текущей сортировки.
2. Расширить `TaskEntity`, `TaskDto`, `TaskCreateRequest`, маппер и frontend-тип задачи. Централизовать правила статуса и страницы в `TaskService`.
3. При создании учитывать страницу и её статус по умолчанию; запросы старых клиентов без `workspace` обрабатывать совместимо. При обновлении выводить переход из нового статуса и текущей страницы, не доверяя противоречивым значениям клиента.
4. Добавить параметр `workspace` в `GET /{teamKey}/tasks`, `TaskFilter` и `TaskRepositoryImpl`. Применять его в SQL/JPA до пагинации, к выдаче и счётчику, включая поиск по ID. При явном `BACKLOG` убрать действующее исключение `status = backlog`, применяемое без фильтра статуса. Закрепление задачи через `pinnedTaskId` не должно обходить команду и страницу через `OR`.
5. Сохранить существующее поведение API без параметра страницы для остальных потребителей. Обе новые страницы должны передавать его явно, в том числе при загрузке всех задач по фильтрам. Excel-экспорт должен получать страницу и фильтры текущего списка явно.
6. Учитывать перемещения в истории. Ограничить расчёт и сдвиг `display_order` парой `(team_key, workspace)`: копия располагается рядом с исходником, переносимая задача добавляется в конец целевого списка. Использовать групповые SQL-обновления затронутого диапазона, не перенумеровывать все задачи обеих страниц.

Результат: сервер однозначно разделяет задачи и атомарно меняет статус вместе с принадлежностью к странице.

## Этап 2. Две страницы на общей реализации

1. Выделить общую страницу списка задач из `BacklogPage.tsx` с настройками страницы: `workspace`, заголовок, статусы фильтра, статус создания/копирования и доступные действия.
2. Сохранить текущий адрес `/{teamKey}/` за дорожной картой для совместимости ссылок; добавить `/{teamKey}/backlog`. Обновить меню, заголовки вкладок и справку в `App.tsx` и `pageTitles.ts`.
3. Переиспользовать `BacklogTaskCard` для обеих страниц. Сохранить редактирование описания, DoD, приоритета, кварталов, релиза, стримов, заказчиков, участников, оценок и распределений по спринтам.
4. При копировании явно задавать статус страницы. Сейчас копирование наследует статус исходной задачи, что не соответствует новой задаче.
5. Разделить настройки фильтров, сортировки, пагинации и видимости участников для дорожной карты и бэклога, а также по командам. Перенести прежние настройки в дорожную карту и нормализовать сохранённые статусы фильтра.
6. После смены страницы обновлять затронутые списки и счётчики через RTK Query; при ошибке восстанавливать исходное состояние. Учитывать накопленные страницы infinite scroll и закрепление новой задачи. Не добавлять созданную задачу во все кешированные списки; детали см. в ревью производительности ниже.
7. Обновить ссылки из «По сотрудникам», переходы после `apply` и открытие задач по ID. Старые ссылки должны находить задачу и при необходимости вести на её актуальную страницу.

Результат: две независимые страницы с одинаковыми атрибутами задач и корректными переходами.

## Этап 3. Jira и расчёт нагрузки

1. На странице бэклога убрать добавление в корзину Jira, массовое добавление и запуск мастера. Возможность просмотра уже существующих Jira-ссылок сохранить.
2. Проверять допустимость экспорта в `JiraIssueExportService` по актуальной задаче, включая отложенную обработку batch: задачи `BACKLOG` не должны создавать Story или задачи участников в Jira.
3. При переносе задачи с дорожной карты в бэклог удалять её из текущей корзины. Проверка на сервере должна обрабатывать и устаревшую корзину.
4. В агрегатах занятой нагрузки и выдаче «По сотрудникам» исключать весь `BACKLOG`, включая отменённые задачи. Сохранить прежние правила учёта задач дорожной карты.
5. Сами введённые нагрузки бэклога сохранять как данные задачи; после перевода в работу они становятся учтённой нагрузкой. Проверить согласованность «Нагрузки», «По сотрудникам» и входных данных планировщика.
6. Проверить Excel-экспорт и другие потребители списка задач, чтобы добавление параметра страницы не меняло их область данных неявно.

Результат: будущие задачи можно оценивать и распределять, они не занимают рабочую ёмкость и недоступны для создания задач в Jira.

## Этап 4. Передача в существующее планирование

Этот этап описан для рабочего допущения о сохранении ID исходной задачи.

1. Добавить явное действие «В планирование» в бэклоге. Оно создаёт связанную заготовку в общем planning backlog; дальнейший выбор справа, preview и review остаются существующими.
2. Добавить необязательную связь `sourceTaskId` в `planning_backlog_items`, DTO и маппинг. Обеспечить принадлежность одной команде на сервере и в ограничениях связи БД; добавить уникальность ненулевого источника. Повторный клик возвращает уже существующую заготовку. Передачу выполнять одним серверным запросом в транзакции, без последовательности загрузки и копирования полей на клиенте.
3. Переносить название, описание, DoD, приоритет, заказчиков, стримы, релиз, стартовый квартал и окно планирования. Оценку конкретного активного участника получать из суммы его распределений; не складывать повторно `loads` и `allocations`. Неактивных участников не превращать в новые demand-строки. Их существующие связи и данные сохраняются у исходной задачи; необходимость перераспределения оставшейся оценки показывать явно.
4. По уточнению пользователя от 01.11.2026 сохранять явно назначенного активного участника без оценки как demand с `days=0`: он виден в диалоге, review и итоговой задаче, но не получает распределений и не занимает ёмкость. Роли и новых исполнителей автоматически не назначать.
5. При `apply` связанную задачу обновлять утверждёнными полями и распределениями, сохраняя ID и поля, которые пользователь не редактировал. Список участников нельзя заменять только участниками нового расчёта: существующие неактивные участники, их заметки, Jira-связи и прежние распределения сохраняются, если пользователь явно не удалил строку из задачи. Итоговые `loads` пересчитать из сохранённых и утверждённых строк без двойного учёта. Для обычной заготовки без источника оставить существующее создание новой задачи только с активными участниками.
6. Определять целевую страницу по итоговому статусу: обычный результат с распределениями получает `inprogress` и `ROADMAP`; существующий сценарий без нагрузки и со статусом `backlog` остаётся в бэклоге.
7. После успешного применения удалять заготовку в той же транзакции. Повторное применение не должно создавать дубликат. Удаление заготовки не удаляет исходную задачу.
8. Обрабатывать удаление, отмену, ручной перевод в работу или изменение исходника после передачи: проверять актуальность источника до применения и возвращать понятный конфликт вместо перезаписи новых данных. Дневной `updatedAt` недостаточен для такой проверки; хранить ревизию исходника и увеличивать её при изменении участников, нагрузок и других значимых для плана данных. Одного `@Version` на родителе недостаточно, если изменение дочернего распределения его не обновляет. Источник и заготовку блокировать на время применения, несколько источников — в одинаковом порядке ID; блокировки не держать во время работы solver. При удалении исходника удалять его заготовку транзакционно; устаревшее применение завершается конфликтом.
9. Обновить тексты review: там могут быть как создаваемые, так и обновляемые задачи. Сохранить восстановление preview из `sessionStorage` и существующую ручную правку.

Изменения ограничены подготовкой входных данных и применением результата. `AlgorithmPlanningSolver` и его правила остаются прежними.

## Этап 5. Доступные релизы

1. Для назначения в карточке предлагать `promDate >= today`. Кварталы фильтра страницы не ограничивают подсказки назначения: задача квартала Q4 может выпускаться в Q1. Использовать одинаковое правило в дорожной карте, бэклоге, planning-диалоге и review.
2. В подсказках фильтра страницы показывать релизы, чья дата ПРОМ входит хотя бы в один из выбранных кварталов. Здесь не применять ограничение `>= today`: прошлый квартал должен оставаться доступен для поиска. Использовать реальные `startDate/endDate` кварталов, а не вычислять квартал по названию.
3. Если кварталы не выбраны, предлагать все релизы команды. При нескольких кварталах объединять их интервалы, не включая промежуточные невыбранные кварталы. При выборе только «Без квартала» не вводить ограничение по дате релиза; при выборе вместе с обычными кварталами применять интервалы обычных кварталов.
4. Последнее уточнение пользователя имеет приоритет: списки являются подсказками, а не ограничениями допустимых дат. В задаче и фильтре всегда можно ввести любую валидную дату вручную, в том числе прошлую, вне выбранных кварталов или отсутствующую в справочнике. При смене кварталов или наступлении нового дня выбранную дату сохранять, даже если она исчезла из подсказок. Предыдущее предложение об автоматическом сбросе даты отменено. Остальные фильтры задач, включая кварталы, продолжают применяться совместно с явно введённой датой.
5. Переиспользовать общий компонент ввода даты релиза с подсказками: `ДД.ММ.ГГГГ` в интерфейсе, строгий разбор календарной даты, `YYYY-MM-DD` в API. При необходимости поддержать ISO-ввод тем же парсером. Сохранять только по Enter, завершению ввода/blur или выбору варианта; неполную/невалидную дату показывать ошибкой и не отправлять. Не достаточно просто включить `allowCustom`: общий компонент сейчас может отправлять строку на каждый символ, а API ожидает UUID.
6. Для фильтра добавить явный параметр `releasePromDate` в API обычных задач, planning backlog и Excel-экспорта. Фильтровать по точной дате связанного релиза в БД. Не отправлять дату в `releaseDateId` и не превращать ошибку разбора в отключение фильтра. Ввод даты в фильтре не создаёт запись релиза: если совпадений нет, выдача пустая. Если переданы и ID, и дата, явно проверить согласованность либо отклонить запрос. Сохранённые фильтры должны поддерживать дату вне полученных подсказок.
7. Для задачи и planning item добавить альтернативный вход `releasePromDate`: если релиз такой даты уже существует в команде, использовать его ID; если не существует — создать релиз и связать с задачей в той же транзакции. Это рабочее решение для требования «дата отсутствует в списке/справочнике». Создание календарных этапов переиспользует существующие правила `ReleaseService`; запись не создавать при каждом символе и при простом поиске. Отмена несохранённого planning-диалога не создаёт релиз. Ответ возвращает канонические ID и дату.
8. Защитить поиск/создание уникальностью `(team_key, prom_date)` и атомарным upsert, чтобы параллельный ручной ввод не создавал дубликаты. Сейчас `ReleaseService` проверяет существование запросом, но в просмотренных миграциях нет такой уникальности. Перед ограничением проверить существующие дубли и определить их объединение с сохранением ссылок и календарных данных. Релиз другой команды не использовать. Не выполнять отдельную загрузку всего календаря перед каждым сохранением.
9. Предлагаемый API подсказок: сохранить полный `GET /releases` для календаря и добавить лёгкий `GET /releases/options` с полями `id`, `name`, `promDate` и параметрами `quarterId`, `fromDate`. Ограничения подсказок применять в БД по `team_key` и диапазонам `prom_date`; интервалы кварталов проверяет сервер. Кешировать отдельно по команде и нормализованным параметрам. Не создавать серверный кеш или отдельный поиск на каждое нажатие клавиши без измеренной необходимости.
10. Оба списка подсказок получать один раз на страницу, а не для каждой карточки. Фильтрацию введённого текста выполнять локально. Для отображения текущего релиза возвращать его краткие данные вместе с задачей/заготовкой; не делать запрос на каждый релиз. Новое назначение возвращает канонический релиз, которым обновляется карточка; подсказки и календарь инвалидировать только при фактическом создании релиза.
11. Ранее назначенный прошлый релиз отображать и сохранять без автоматической очистки; при копировании задачи тоже сохранять, поскольку теперь ручное назначение той же даты допустимо. Прошедшую дату можно пометить, но не блокировать.
12. Согласовать календарную дату frontend/backend в одной бизнес-таймзоне; для текущего окружения предлагается `Europe/Moscow`. Обновлять подсказки при наступлении нового дня и возврате на вкладку; не создавать таймер на каждую карточку. На backend использовать внедряемый `Clock` для воспроизводимых проверок границы дня.
13. UX-оговорка: квартал задачи и квартал её релиза могут различаться. При выбранном Q4 задача с релизом Q1 остаётся в списке задач; её релиз можно ввести вручную, хотя его нет в подсказках Q4. Подписать поле «Релиз (ПРОМ)» и дать подсказку «Выберите из списка или введите дату». При загрузке новых вариантов не терять текущий ввод и не заменять выбранную дату устаревшим ответом.

## Этап 6. Деактивация участников

Проверка текущего кода показала, что основное требование уже реализовано:

- `ParticipantService.delete()` устанавливает `active=false`, не удаляет запись и не удаляет связи с задачами. Повторная деактивация безопасна.
- `getParticipants` во frontend запрашивает `includeInactive=true`; этот общий справочник используется карточками. `useActiveParticipantsQuery` отбирает активных из того же кеша для страницы команды.
- `BacklogTaskCard` строит существующие строки по назначенным ID без фильтра активности и показывает «Неактивен». Варианты добавления/замены ограничены активными.
- `TaskService.addParticipant`, замена участника и создание новых связей в `updateParticipants` проверяют активность. Уже существующий неактивный участник может сохраняться в списке участников при редактировании задачи.
- Копирование исключает неактивных из новой задачи. Solver выбирает только активных. Исторические Jira-ссылки сохраняются, новые Jira-задачи на неактивного исполнителя не создаются.

Эту логику сохранить при разделении страниц. На деактивации не фильтровать `participantIds` задач, не очищать нагрузки, заметки, прежнего лидера и ссылки Jira, не удалять участника из общего кеша. Автоматического восстановления активности не делать.

При копировании исключить неактивных из новой задачи, а итоговые нагрузки получить из скопированных активных распределений. Не наследовать суммарные `loads` исходника с долей исключённого исполнителя: иначе возможна нагрузка без участника, особенно если в исходнике были только неактивные исполнители.

Удаление строки исполнителя из конкретной задачи — другая операция: текущий `TaskService.removeParticipant` действительно удаляет связь и связанные данные этой задачи. Она не равна удалению участника из команды; различие нужно сохранять в названиях действий и проверках.

Для производительности оставить один общий кеш справочника команды, производный список активных и `Map` для карточек. Не делать отдельный запрос на каждого неактивного исполнителя. Если запись временно отсутствует в словаре, строку назначения не следует молча терять: показывать состояние загрузки/недоступных данных и не сохранять урезанный список участников.

Проверки охватывают обе новые страницы, перезагрузку, редактирование существующей задачи, смену порядка, копирование, передачу в планирование и применение результата. Сохранение исходной задачи при `apply` не должно автоматически удалять неактивных. Если участник деактивирован уже после preview, требовать обновления плана для новых назначений, сохраняя исторические строки.

Если в работающем окружении участник исчезает, причина пока не установлена. Проверить фактические версии frontend/backend, применение миграции `1.0.0_21_participant_active.sql`, ответ `GET /participants?includeInactive=true` и сохранность связей `task_participants`; не считать локальный mocked e2e доказательством состояния стенда.

Фактическая проверка 31.10.2026: существующий Playwright-тест `deactivation hides the participant from the team and preserves the task row` прошёл (1/1). Он проверяет сохранение строки и отметки после перезагрузки, а также исключение неактивного из копии; API замокан. `ParticipantServiceTest` и `TaskServiceParticipantTest` прошли (9/9). Для запуска на установленной Java 25 потребовались явное подключение Byte Buddy agent и `net.bytebuddy.experimental=true`; настройки проекта не менялись. Обычный запуск следует выполнять на поддерживаемой проектом Java 17. Реальный backend и рабочая база этой проверкой не охвачены.

## Этап 7. Проверки и критерии приёмки

Backend:

- Миграция на пустой базе и копии существующей схемы: заполнение `workspace`, замена старых статусов по заданной таблице, отсутствие потерянных задач.
- Переходы из таблицы правил, особенно отмена на каждой странице, статусы создания и копирования.
- Серверная фильтрация, пагинация, счётчики и изоляция команд.
- Отказ экспорта бэклога в Jira, включая смешанный запрос и задачу, перемещённую после постановки в batch.
- Бэклог, включая отменённые задачи, не влияет на занятую ёмкость.
- Передача в планирование, повторная передача, обновление исходника с тем же ID, отсутствие двойного учёта и конфликт при устаревшем источнике.
- Ручная дата в фильтре не создаёт релиз и не отключает фильтрацию; ручная дата в задаче переиспользует либо атомарно создаёт релиз своей команды. Валидировать невозможные даты, конфликт ID/даты и параллельное создание.
- Деактивация не удаляет участника и связи; запрет новых назначений действует через отдельное добавление, замену, создание, полное обновление задачи и применение плана. Старое назначение сохраняется при редактировании существующей задачи.
- Регрессия существующих `PlanningWorkbenchServiceTest` и `AlgorithmPlanningSolverTest`.

Frontend / Playwright:

- Навигация, заголовки и независимые сохранённые фильтры двух страниц.
- Создание и копирование дают статус своей страницы, включая копирование выполненной или отменённой задачи.
- Смена статуса переносит карточку без потери данных; отмена сохраняет страницу; перезагрузка подтверждает результат.
- Сортировка, участники, редактирование нагрузок, история и копирование работают на обеих страницах.
- В бэклоге отсутствуют действия создания в Jira; перемещённая задача удаляется из корзины.
- Цепочка `бэклог → планирование → preview → reload → apply → дорожная карта` на реальном backend без дубликата исходной задачи.
- Релизы вчера/сегодня/завтра, ранее сохранённый прошлый релиз, копирование и граница календарного дня.
- Кварталы подряд и с пропусками, границы квартала/года, пустой выбор, «Без квартала», смена кварталов с сохранением выбранной даты и отсутствие лишнего запроса задач.
- Ручная дата вне подсказок и справочника, прошедшая дата, ввод Enter/blur, отмена диалога, неполная дата и `31.02`: данные не сбрасываются, ошибка не сохраняется, запросов на каждый символ нет.
- После деактивации участник исчезает из команды и вариантов добавления, но остаётся в прежних задачах с отметкой «Неактивен», нагрузкой, заметками, лидером и Jira-ссылками, в том числе после перезагрузки и применения плана.
- Старые статусы преобразованы в задачах и сохранённых настройках; очистка фильтра и переход по старой ссылке не смешивают страницы.
- Переключение команд и страниц, создание при нескольких кешированных фильтрах, смена размера страницы: данные и optimistic updates не смешиваются.

Проверки реализации: `npm run typecheck`, `npm run build`, `npm run e2e`, backend `mvn -q -Drevision=0.1.0 test` из `server/`. Затем `npm run e2e:real` при запущенных backend и PostgreSQL; подтвердить миграцию на PostgreSQL отдельно от mocked e2e.

### Что оставить простым

- Одна таблица реальных задач, один сервис переходов, общая карточка и страница с явными настройками режима. Не создавать две независимые реализации.
- Сохранить у `/tasks` существующую схему `count → ID страницы → batch-загрузка деталей`. Не соединять все коллекции одним fetch join: это размножает строки.
- Варианты релизов получать общим запросом страницы и переиспользовать массив и `Map<id, option>`. Мемоизировать производные списки в одном месте; не пересортировывать их для каждой карточки.
- Ручной ввод даты не требует поиска по сети на каждый символ. Для фильтра достаточно одного запроса задач после подтверждения даты; для назначения — одного серверного сохранения с разрешением даты в ID релиза. Новый серверный парсер должен различать дату и UUID явно.
- Справочник участников уже общий для активных и неактивных: сохранить кеш и производные выборки. Деактивация обновляет флаг, а не вырезает запись из кеша, используемого историческими задачами.
- Не добавлять виртуализацию, WebSocket, внешние кеши, новые библиотеки и денормализованные агрегаты без профиля нагрузки. Если рендер накопленных карточек окажется узким местом — отдельно измерить React Profiler и затем выбрать ограничение накопления или виртуализацию.
- Не запускать solver при смене фильтров, обновлении релизов или передаче заготовки. Расчёт остаётся явным действием пользователя.
- Применение плана выполняется в транзакции с ограничением числа запросов на задачу. Общие справочники участников/спринтов/релизов для пакета загружать один раз; не вызывать полную цепочку получения всех справочников для каждой задачи, если измерения подтверждают повторную работу.

### Индексы и проверка результата

- Кандидат для обычного списка задач: `(team_key, workspace, display_order, created_at, id)` в порядке фактического `ORDER BY`; сопоставить с существующими индексами и проверить `EXPLAIN (ANALYZE, BUFFERS)` перед добавлением дублирующих индексов.
- Для вариантов релизов: `(team_key, prom_date, id)`; SQL использует сравнение `prom_date` с диапазонами, а не `EXTRACT(quarter FROM prom_date)`.
- При введении уникальности `(team_key, prom_date)` проверить, покрывает ли этот индекс выборки подсказок без отдельного почти дублирующего индекса. Точную форму выбрать по плану запроса.
- Для источника planning item: уникальный индекс по ненулевому `source_task_id` и проверяемая принадлежность команде. Это защита повторной передачи, в том числе параллельной.
- На одинаковом наборе данных сравнить до/после число HTTP и SQL-запросов, размер ответа и p50/p95: открытие страницы, смена квартала, одна правка текста, перенос задачи, открытие planning backlog и применение пакета. Нужны в том числе наборы в 100, 1 000 и 10 000 задач; числа являются размерами проверочных наборов, а не заявленным текущим объёмом.
- На переключении кварталов должен уходить один запрос задач с окончательными фильтрами и не более одного запроса соответствующих вариантов релизов при промахе кеша. Правка описания не запрашивает релизы и не пересчитывает ёмкость.
- Для обычных списков SQL-count не должен расти пропорционально количеству элементов страницы или общему числу задач; для пакетного `apply` отдельно измерять стоимость на задачу. Проверки проводить на PostgreSQL 15, указанном в `docker-compose.yml`.

Основания для решений по кешированию: [RTK Query Cache Behavior](https://redux-toolkit.js.org/rtk-query/usage/cache-behavior) и [Automated Re-fetching](https://redux-toolkit.js.org/rtk-query/usage/automated-refetching). Порядок полей индекса проверять с учётом [документации PostgreSQL 15](https://www.postgresql.org/docs/15/indexes-multicolumn.html).

- Серверные unit-тесты: 90; существующие mocked browser e2e: 12; реальные сценарии планирования: 5; новые реальные сценарии дорожной карты/бэклога: 3.
- Новые реальные проверки охватывают сохранение ID и неактивных исполнителей при apply, ручной ввод прошлой даты в карточке и фильтре, отсутствие создания релиза при поиске, переход страницы по статусу, конкурентное создание одного релиза, повторную передачу в планирование, конфликт старого источника, ограничение Jira и квартальные подсказки.
- PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` на 10 000 временных tasks и planning items: обычная выборка 20 ID задач использует `tasks_workspace_order_idx` (около 0,06 мс), planning items — существующий индекс с incremental sort (около 0,08 мс). Count задач — около 3,4 мс. Все временные строки откатились транзакцией. Это отдельные локальные SQL-замеры без HTTP, загрузки деталей и рендера; они не являются p95 приложения и не заменяют профиль сложных фильтров/сортировок.
- Общий кеш участников сохранён. Кеши списков различаются по workspace, команде, размеру страницы и фильтрам; при смене команды старые общие справочники сбрасываются. Подсказки релизов имеют краткую проекцию, ручной ввод коммитится после проверки даты.

Итоговая проверка кеширования: реальный browser e2e подтверждает, что редактирование описания без активного поиска не выполняет повторный GET списка задач. При изменении полей, влияющих на выбранные фильтры или сортировку, обновляется соответствующий кеш запроса; переход статуса обновляет списки обеих страниц.
