Обновлено 01.11.2026. Все шесть замечаний предыдущего ревью исправлены. Для F1 принято уточнение пользователя: явно назначенный участник без оценки сохраняется в заготовке, preview и итоговой задаче с нулевой нагрузкой. Solver не получает положительную работу для такого назначения.

## Закрытие замечаний F1–F6

| Замечание | Исправление | Подтверждение |
| --- | --- | --- |
| F1: терялся активный участник без оценки | Transfer сохраняет demand конкретного участника с `days=0`; нормализаторы и диалог сохраняют его; solver пропускает нулевую работу; apply сохраняет назначение без allocations/loads. Явное удаление участника в review остаётся допустимым | Реальный браузер: transfer → сохранение диалога → preview → apply; проверены участник, пустая нагрузка, заметка и лидер |
| F2: нельзя очистить лидера/заметку, source metadata отсутствовали в review | Единая миграция 22 добавляет поля snapshot заметок и лидера в заготовке. Прежние независимые drafts остаются без связи с источником. DTO передаёт его в review без N+1 чтений источников. Пропущенный `leaderId` не меняет лидера, `""` очищает; пустая заметка удаляет значение. UI передаёт явные удаления заметок. Старый session preview требует нового расчёта | Реальный API: сохранение пропущенных полей и явная очистка. Браузер проверяет исходную заметку в диалоге review |
| F3: после загрузки второй страницы оставались задачи вне поиска | При инвалидации planning перечитывает и заменяет весь ранее загруженный префикс; обычная загрузка следующей страницы добавляет только её | Реальный браузер на 23 задачах: редактирование с исключением из поиска, удаление и создание после загрузки второй страницы |
| F4: Excel определял раздел по имени команды | Workspace передаётся из маршрута явно; callback обновляется при переходе между страницами; учтён завершающий `/` | Реальный браузер: команда с `backlog` в ключе, экспорт дорожной карты и затем бэклога |
| F5: выбранный релиз отображался UUID | Выпадающий список и ручной ввод сохраняют ISO-дату. Отображение больше не зависит от наличия варианта в текущих подсказках; доступные старые ID переводятся в дату | Реальный браузер: выбор даты, исключение её квартала, перезагрузка страницы — отображается прежняя дата |
| F6: общие справочники и DTO загружались для каждой задачи | `TaskService.applyPlanningBatch` разделяет спринты, участников, релизы, кеш кварталов и порядка; обогащение Jira выполняется общим запросом. Валидация planning использует уже загруженные спринты; разрешение patch-полей кешируется по ID/дате. Новые задачи добавляются в конец целевого списка в порядке выбранных заготовок, без массовых сдвигов на каждом шаге. Существующие несохранённые строки нагрузки берутся из агрегата задачи | Параметризованные серверные проверки на 1/10/100 задач: постоянное число чтений справочников, один запрос порядка, отсутствие массового сдвига при добавлении; проверены назначения и нагрузки. Реальный HTTP/SQL замер ниже |

Проверка всего изменённого пути не выявила новых блокирующих дефектов после исправлений. При оптимизации дополнительно исправлена зависимость пересчёта нагрузки от промежуточного auto-flush: поиск строки сначала использует уже созданную строку в агрегате, что предотвращает создание двух объектов с одинаковым составным ключом.

## Измерение пакетного применения

PostgreSQL 15, Java 25, локальный backend, реальные HTTP-запросы и Hibernate session statistics. Временная команда, один участник, один спринт, общий релиз, по одному дню на задачу; запрос содержит UI-поля `itemPatches`. Измерялось количество prepared JDBC statements основной транзакции apply. Отдельные API-события истории по `X-Session-Id` в этом профиле отключены. Сами задачи и связи сохраняются обычным ORM-путём в одной транзакции.

Первый замер после переиспользования справочников выявил квадратичную работу из-за принудительного flush при ненужном массовом сдвиге порядка. После исправления количество запросов стало линейным:

| Задач | SQL до оптимизации порядка | SQL после | Время до, мс | Время после, мс |
| --- | --- | --- | --- | --- |
| 1 | 28 | 26 | 190.3 | 176.4 |
| 10 | 325 | 116 | 624.1 | 256.7 |
| 100 | 21115 | 1016 | 24203.4 | 1352.9 |

Это одиночные локальные измерения, не p50/p95 и не результат конкурентного нагрузочного теста. Число записей/изменений самих задач закономерно растёт с размером пакета. Серверные регрессии отдельно контролируют постоянное количество чтений общих справочников. Для обычной валидации planning и мутации задач существуют отдельные ограниченные чтения команды; это постоянные расходы пакета, а не чтение для каждого элемента.

## Проверки и границы покрытия

- 93 серверных теста, TypeScript и production-сборки frontend/backend.
- 12 browser e2e с моками и 13 browser e2e с реальным backend/PostgreSQL, включая пять новых регрессий.
- После объединения ветка содержит только миграцию 22; повторно проверены обновление существующей базы и создание чистой схемы с Hibernate validate. Резервная копия до основной миграции: `/tmp/sprints-planning-before-roadmap.sql`.
- Общий профиль API p50/p95 и React render на 100/1 000/10 000 задачах не снят. Ранее приведённые EXPLAIN на 10 000 строках подтверждают только конкретные SQL-выборки.
- Внешняя Jira проверялась в mock-режиме. Реальных запросов создания задач во внешней Jira не выполнялось.
- Локальный frontend: http://localhost:4173/#/customlab/ ; backend: http://localhost:8080/api/v1/sprints-planning/actuator/health . Временные тестовые команды удаляются; пользовательские команды не изменяются.

## Объединение миграций ветки

Изменения 22 и 23 объединены в один файл и один changeset `sprints:1.0.0-22`. Удалены дублирующий `tasks_status_check` и backfill snapshot-полей: при обновлении с версии 21 все новые `source_task_id` равны NULL. Обновление статусов и workspace объединено в один UPDATE; однотипные ALTER объединены. Составной FK, уникальность источника и дат релиза, рабочий индекс и все шесть новых столбцов сохранены.

Для локальной базы, где прежние варианты 22/23 уже запускались, согласование истории проводится отдельно после резервного копирования и проверки эквивалентности схемы. При первом выпуске из версии 21 дополнительные действия с историей Liquibase не нужны. Предполагается, что прежние варианты ещё не выпущены в общие окружения.

Объединённый SQL также проверен на временных таблицах: все шесть прежних статусов, сохранение строк, отклонение неизвестного статуса без лишнего CHECK, согласованность workspace, составной FK, уникальность источника и атомарный откат при дубле даты релиза. Локальная схема сравнена с результатом обновления копии; совпадение подтверждено за исключением удалённого CHECK. После резервной копии `/tmp/sprints-planning-before-migration-merge.sql` согласованы только локальные записи changeset 22/23; хеши tasks, planning items, releases, participants, loads и allocations до и после совпали. В итоговом JAR присутствует только SQL-файл 22.

После объединения выполнена чистая сборка backend и повторно пройдены все 13 real-backend browser e2e. Основной локальный backend перезапущен с объединённым changeset; временные базы проверки удалены.
