# Смена квартала: проверка задержки и рендеров

Предыдущие проверки начальных API-запросов и локального ввода не покрывали замену длинного списка тяжёлых карточек. Задержка на дорожной карте и в бэклоге воспроизвелась; вывод о достаточной оптимизации этой цепочки был преждевременным.

## Причины

1. `useGetTasksQuery` выбирал `data`, сохранявшую задачи предыдущего фильтра. При выборе нового квартала эти карточки уже получали новый набор спринтов и перестраивали таблицы, хотя затем заменялись ответом другого запроса.
2. Нагрузка копировалась из RTK Query в локальное состояние эффектом. Новые задачи сначала монтировались с пустым `allocationsByParticipant`, затем все карточки обновлялись повторно с нагрузкой. Количество ячеек не было единственным фактором: каждая карточка содержит несколько MUI-редакторов, таблицу и DnD.
3. `startTransition` вокруг Redux-dispatch не делал обновление внешнего хранилища прерываемым, но создавал дополнительные pending-обновления страницы.
4. На каждом обновлении списка создавались новые options сенсоров DnD, массив sortable ID и dragHandle. Это мешало `React.memo` даже при неизменных данных карточки.
5. Даже после удаления повторных проходов однократный монтаж всех двадцати карточек оставался дорогим. По мере серверной догрузки DOM продолжал расти.
6. `forceRefetch` сравнивал фильтры через исходный `JSON.stringify` после канонизации cache key. Перестановка одинаковых кварталов поэтому всё равно вызывала запрос. Такая же проверка была в endpoint планирования.

## Реализация

- Для списка используется `currentData`: задачи прошлого фильтра не перестраиваются под новые колонки.
- Источник нагрузки — существующий кэш RTK Query. Удалены локальная копия и эффект синхронизации. Оптимистические изменения и откаты выполняются существующими mutation lifecycle. Изменение ячейки сохраняется одним вызовом мутации. Копирование, сдвиги, удаление и замена участников используют тот же источник данных.
- Команды, которым нужны актуальные данные в момент клика, читают страницу стандартным selector RTK Query через `useStore`. Нет callback-ref обходов зависимостей и нового кэша.
- Удалены `useTransition` вокруг Redux-операций. Для списка добавлена обычная мемоизированная граница с `useDeferredValue`: данные, кварталы и обработчики переходят в новую версию вместе. Сетевые запросы не откладываются. При смене фильтра старая версия временно обозначена как обновляемая; её элементы управления заблокированы до смены версии. Обычное обновление ячейки не блокирует соседний редактор.
- Стабилизированы options сенсоров, массив sortable ID и dragHandle.
- Для списков длиннее четырёх задач используется `@tanstack/react-virtual` с оконной прокруткой, измерением реальной высоты и запасом в одну карточку. Редактируемая и перетаскиваемая карточки остаются смонтированными при выходе за пределы экрана. Длина серверной страницы и число загруженных задач не уменьшались.
- `forceRefetch` задач и планирования учитывает только смену страницы внутри объединённой cache entry. Остальные параметры уже входят в канонический ключ. Инвалидация и явный refetch сохраняют своё поведение.

Основания для выбора стандартных механизмов: [React: внешнее хранилище и transitions](https://react.dev/reference/react/useSyncExternalStore#caveats), [React: useDeferredValue](https://react.dev/reference/react/useDeferredValue), [TanStack: оконный список](https://tanstack.com/virtual/latest/docs/framework/react/examples/window), [TanStack: динамические размеры](https://tanstack.com/virtual/latest/docs/framework/react/examples/dynamic). Для DnD сохранены `DragOverlay` и `verticalListSortingStrategy`, поддерживающая виртуальные списки согласно [документации dnd-kit](https://dndkit.com/legacy/presets/sortable/overview/).

## Условия замера

Две страницы, по 20 задач на квартал, четыре участника и шесть спринтов у каждой задачи. Два квартала содержат разные задачи. API воспроизводится фиксированными ответами с задержкой 150 мс, чтобы отделить работу React и браузера от скорости базы и сети. Переключение — выбор второго квартала и снятие первого; обратный переход использует уже посещённый квартал. Это два действия множественного фильтра, а не один DOM-click.

Development-проверка выполнялась с `StrictMode`. Зафиксированы выполнявшие работу commits карточек и длинные задачи браузера. В production нет счётчиков рендеров.

| Development, тот же набор данных | До исправления | После |
| --- | ---: | ---: |
| Карточек в DOM в начале списка | 20 | 2 |
| Первоначальное отображение | 20 карточек дважды, сначала без нагрузки | Две видимые карточки однократно, сразу с нагрузкой |
| Переход на новый квартал, вся последовательность | 8,3–8,4 с | 0,67–0,70 с |
| Обратный переход, вся последовательность | 8,9 с | 0,56–0,61 с |

Время всей последовательности включает работу браузерной автоматизации и ожидание `networkidle`, поэтому это не чистое время React-render. Число две зависит от размеров окна и высоты карточки; это результат конкретного набора, а не фиксированный лимит интерфейса.

Для production сравнивались сохранённая сборка перед исправлением и итоговая сборка на тех же ответах API. CPU Chromium замедлен в четыре раза после начальной загрузки. Три прогона каждой версии, в таблице медианы; максимальная блокировка — медиана самого длинного `longtask` внутри соответствующей последовательности каждого прогона.

| Production, CPU ×4 | Вся последовательность до → после | Максимальная блокировка до → после |
| --- | ---: | ---: |
| Дорожная карта, новый квартал | 15,75 → 0,96 с | 3718 → 361 мс |
| Дорожная карта, обратный переход | 12,85 → 1,47 с | 4096 → 177 мс |
| Бэклог, новый квартал | 16,04 → 0,97 с | 3712 → 362 мс |
| Бэклог, обратный переход | 12,85 → 1,02 с | 4125 → 177 мс |

За полный цикл запросов задач стало три вместо четырёх: повторный запрос того же набора кварталов при изменении порядка выбора отсутствует. Ошибок JavaScript в этих прогонах нет. Замедление CPU специально усиливает различия и не является оценкой времени открытия на устройстве пользователя. Даже после исправления на таком CPU возможны долгие кадры; результат — существенное уменьшение блокировок, а не обещание отсутствия всех задержек.

Дополнительный контрольный production-прогон без замедления CPU: весь переход на новый квартал занял 425–437 мс, обратный — 252–262 мс. Максимальный `longtask` составил соответственно 101 мс и 54–55 мс. Это один контрольный прогон обеих страниц; он не заменяет медианы трёх прогонов выше. Открытие страницы и переход на страницу релизов также проверены на production-сборке без ошибок JavaScript.

## Регрессионные проверки

`npm run typecheck`, `npm run build`, 21 тест с моками и 29 с реальным API/PostgreSQL прошли. Новые сценарии — `tests/e2e/task-rendering.spec.ts`:

- На обеих страницах монтируются только ближайшие карточки, сразу с нагрузкой; нет повторного обновления каждой новой карточки эффектом.
- Возврат к кварталу и перестановка одинакового набора кварталов используют кэш.
- Черновик описания и фокус сохраняются при прокрутке до конца; изменение высоты не накладывает соседние карточки друг на друга.
- Следующая серверная страница догружается один раз, отображаются итог и последняя задача.
- Изменение ячейки не обновляет соседние карточки; ошибка API откатывает значение.
- Перетаскивание сохраняет порядок. Копирование строки в следующий квартал, сдвиг строки и сдвиг всей задачи используют актуальную нагрузку.

Виртуализация ограничивает DOM, а не загруженные данные. Поиск по всем задачам выполняется фильтром приложения; браузерный поиск видит только смонтированные карточки. Производительность на других устройствах и данных может отличаться; абсолютное отсутствие долгих кадров не гарантируется.
