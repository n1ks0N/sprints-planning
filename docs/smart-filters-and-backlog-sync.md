# Кварталы, релизы и карточки задач

## Реализованное поведение

1. После успешного создания задачи выбранный квартал записывается в `task.creationQuarter.v1:<teamKey>`. Это общее значение для дорожной карты и бэклога одной команды. «Без квартала» сохраняется отдельно от отсутствующего значения. При отсутствии, удалении или завершении сохранённого квартала используется текущий, при отсутствии текущего в справочнике — «Без квартала». Изменение выбора без создания и неуспешное создание сохранённое предпочтение не меняют.
2. Поле создания предлагает текущие и будущие кварталы из справочника команды и «Без квартала». Фильтры и поле создания имеют разные наборы доступных значений.
3. Общий `QuarterFilter` используется на страницах задач, планирования, загрузки сотрудников, ёмкости и настройки кварталов. Подписи выбранных значений содержат только название. Placeholder отображается только при пустом выборе. `GET /quarters/options` без поиска возвращает предыдущий, текущий и следующий календарные кварталы; `search` ищет подстроку названия по всем годам. Поиск регистронезависимый, `%` и `_` считаются обычными символами. Поиск ограничен 100 результатами.
4. Общий `ReleaseFilter` используется на дорожной карте, в бэклоге и планировании. Без поискового текста подсказки соответствуют выбранным кварталам; без выбранных кварталов доступны релизы команды. `GET /releases/options?search=...` ищет по дате ПРОМ в форматах `ДД.ММ.ГГГГ` и `YYYY-MM-DD`, независимо от кварталов. Поиск ограничен 100 результатами. Полную дату можно добавить вручную через Enter или потерю фокуса. При выбранном релизе placeholder скрыт. Это не создаёт запись релиза. Значения нескольких релизов объединяются через ИЛИ; остальные группы фильтров — через И.
5. Старые одиночные фильтры из localStorage преобразуются в массив. Сохранённый ID релиза разрешается отдельным коротким запросом `ids` даже за пределами текущих подсказок, затем хранится дата. Выбранные кварталы и релизы сохраняются при поиске других вариантов.
6. На широком экране карточка отдаёт 40% ширины тексту и 60% параметрам, на узком остаётся вертикальной. Статус, приоритет и релиз компактнее. Пустые описание и DOD показывают только кликабельную подпись. Текст полей — `#333`, подписи сохраняют прежний цвет. Переносы строк сохраняются при отображении описания и DOD, в том числе в подсказке. Удалён поясняющий текст внизу списка задач.
7. На странице сотрудников API по-прежнему отдаёт страницы сотрудников, браузер объединяет их без дублей. Следующая страница загружается по прокрутке или кнопке; показано число загруженных сотрудников. Изменение фильтра или размера страницы начинает загрузку с нулевой страницы. После изменения нагрузки перечитываются уже загруженные страницы, сохраняя полный видимый список. При ошибке доступна повторная загрузка.
8. Сортировка планирования вынесена под блок фильтров, перед содержимым.
9. На странице «Кварталы/Спринты» название меняется через существующую форму редактирования квартала. Пустое название не сохраняется. Переименование не меняет даты, год и номер квартала; при изменении дат пользовательское название сохраняется.

## Производительность и совместимость

- Поисковые запросы отправляются после паузы 250 мс; результаты кэшируются RTK Query с учётом команды и параметров. Во время ожидания нового поиска старые подсказки скрыты, чтобы Enter не выбирал устаревший результат.
- Каталоги кварталов переиспользуются из общего кэша для подписей выбранных значений и календарей. Поиск и окно подсказок вычисляет сервер. Релизы приходят короткой проекцией без лишних связанных данных.
- Множественный фильтр поддерживается в SQL до подсчёта и пагинации, а также в Excel и массовых операциях по отфильтрованному списку. Новые параметры: `releaseDateIds` и `releasePromDates`, значения через запятую. Старые одиночные параметры сохраняются для совместимости.
- Догрузка сотрудников не запрашивает все задачи команды; сохраняется серверная пагинация по сотрудникам. Повторное чтение загруженных страниц происходит при инвалидации после изменения данных.
- Изменений SQL-миграций и структуры базы для этих пунктов нет.
- Причины повторных запросов, владение данными и замеры React описаны в [ревью цепочки API и рендеров](api-render-performance-review.md). На входе фильтр выполняет один запрос релизов после разрешения квартала; справочники для назначения и истории загружаются при открытии соответствующего интерфейса.

## Проверка

- `npm run typecheck` и `npm run build` — успешно. Сборка сохраняет известное предупреждение webpack о размере JS-чанков.
- Maven `package` — 95 тестов успешно; отдельный интеграционный тест нестандартной схемы пропущен без `PLANNING_SCHEMA_TEST_URL`.
- Playwright — 21 тест с моками и 29 тестов с реальным API/PostgreSQL успешно. Проверки покрывают окно кварталов и поиск вне него, поиск дат вне выбранных кварталов, множественный фильтр в задачах/планировании/экспорте, ручной ввод, старые сохранённые фильтры, сохранение квартала только после успешного создания и догрузку сотрудников с обновлением всего загруженного списка. Дополнительно проверены скрытие placeholder, отображение переносов строк, переименование квартала, переключение выбора в планирование и отсутствие лишних рендеров при локальном вводе. Детали — в [аудите фронтенда](frontend-performance-audit.md).
- Карточка и список сотрудников проверены по браузерным снимкам.

# Варианты синхронизации бэклога с планированием — только анализ

Сейчас это разные сущности: страница бэклога показывает `tasks` с `workspace=BACKLOG`, а «Общий backlog» планирования — `planning_backlog_items`. Передача задачи создаёт связанную заготовку с `sourceTaskId` и `sourceRevision`. Повторная передача возвращает существующую заготовку. Изменения заготовки не меняют исходную задачу; при применении планирования исходная задача обновляется с сохранением ID. Если исходник изменился после передачи, применение отклоняется с конфликтом ревизий. Есть и самостоятельные заготовки без исходной задачи.

| Вариант | Как работает | Последствия |
| --- | --- | --- |
| **Единый список кандидатов, заготовка по выбору — рекомендуемый первый шаг** | «Общий backlog» показывает актуальные активные задачи BACKLOG и самостоятельные заготовки. Связанная заготовка создаётся при выборе задачи в текущий план. Наличие заготовки не дублирует задачу в списке. | Убирает необходимость предварительной передачи. Существующая модель и защита ревизиями сохраняются. Нужно единое серверное чтение с фильтрацией, подсчётом и пагинацией, а не склеивание двух списков на фронте. После выбора заготовка остаётся снимком для безопасного моделирования. |
| Общая задача как источник основных полей | Название, описание, DOD, приоритет и релиз хранятся в задаче; планирование хранит потребности, ограничения и черновые изменения. | Больше согласованности при редактировании с разных страниц, но требуется явно отличать сохранённые правки от сценарных. Нужны согласованные версии, транзакции и разрешение конфликтов; самостоятельные старые заготовки требуют отдельного переходного правила. |
| Двусторонняя синхронизация копий | Каждая правка копируется из задачи в заготовку и обратно. | Выше риск циклов, потери сценарных правок и конфликтов при параллельном редактировании; больше записей и инвалидаций. Для текущей архитектуры не рекомендуется. |

Для первого варианта следует заранее определить: самостоятельное создание задач в планировании остаётся или переносится в общий бэклог; какие изменения исходника разрешают обновить снимок без потери ручного плана; как показывать удалённые и отменённые исходники. В любом варианте нагрузка продолжает учитываться только из ROADMAP, до применения планирования заготовки не увеличивают фактическую загрузку. Автоматическая синхронизация в рамках текущей задачи не реализована.
