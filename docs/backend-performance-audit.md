# Проверка производительности backend

Дата: 8 ноября 2026. Исходная точка — рабочее дерево перед этой проверкой, включая предыдущие изменения дорожной карты, бэклога и фильтров.

Версии в `pom.xml` не изменены: Java target 17, Spring Boot 3.4.6, OR-Tools 9.11.4210. Эти значения уже находились в репозитории и отличаются от приведённых в переписке примеров. Сравнение API выполнено на одном OpenJDK 21.0.13 Temurin. Проверки именно на сборке SberJDK не проводились. Сборка использует существующий локальный компилятор с `--release 17`; тесты и исполняемый JAR дополнительно проверены на Java 21.

## Изменения и основания

| Область | Обнаружено | Изменение |
| --- | --- | --- |
| Детали задачи, Jira, связанные задачи планирования | Одновременное JOIN FETCH нескольких коллекций размножал строки | Один общий загрузчик: основная запись и пять отдельных запросов коллекций; фильтрация по команде до загрузки коллекций |
| Списки задач | Повторный запрос уже загруженных релизов, лишняя загрузка лидера с его потоками | Используются загруженные релизы; для идентификатора лидера достаточно прокси |
| Jira и отдельный лидер | Лидер может не входить в участников; после сокращения JOIN его поля могли остаться ленивыми | Полные загрузки одной/нескольких задач дополнительно получают незагруженных лидеров одним запросом; проверено обращение к полям после завершения транзакции и mock-экспорт с отдельным лидером |
| Preview планирования | Дважды определялось окно каждой задачи отдельными запросами | Один запрос спринтов всех выбранных окон, результат используется повторно |
| Применение связанных заготовок | Повторные блокировки и загрузки каждой исходной задачи | Пакетная блокировка исходных задач в порядке UUID, пакетная загрузка, повторное использование в общей транзакции |
| Параллельное удаление и применение | Разный порядок блокировки задачи и заготовки мог создавать взаимное ожидание | В обоих путях сначала блокируется исходная задача |
| Изменения матрицы нагрузки | Чтение существующих ячеек по одной, повторный пересчёт спринта | Используется загруженная коллекция; участники читаются пакетом, каждый затронутый спринт пересчитывается один раз |
| Обычное создание и изменение задачи | Повторные чтения участников в циклах назначения и заполнения нагрузки | Новые участники получаются пакетом; нагрузка переиспользует участников задачи и при необходимости один запрос недостающих |
| Массовое планирование | Повторные запросы одних заказчиков/потоков, промежуточные flush | Справочники загружаются перед пакетом, новые значения переиспользуются; явный flush один на пакет |
| JSONB планирования | У `TaskPlanningDemandValue` отсутствовало сравнение по значению; неизменённые строки обновлялись повторно | Добавлены `equals`/`hashCode`; интеграционный тест проверяет отсутствие UPDATE и сохранение реального изменения |
| История | Новые JSON-снимки провоцировали повторный dirty checking событий | Сущность истории помечена Hibernate `@Immutable`: события добавляются и удаляются при очистке команды, существующие события не редактируются |
| Страница истории | Один запрос действий на каждую сессию | Один PostgreSQL LATERAL-запрос для всех выбранных пар «сессия, пользователь», прежний предел 200 действий на пару сохранён |
| Чтение и пакетная запись | Не все связанные чтения выполнялись в общей транзакции; JDBC batching отсутствовал | `readOnly` для списков, деталей, таблицы сотрудников, capacity и экспорта; Hibernate batch 50, упорядочение INSERT/UPDATE, pgJDBC `reWriteBatchedInserts` |
| Сортировка задач по релизу | `LocalDate.MAX` выходил за диапазон PostgreSQL; запрос возвращал 409 | Используется допустимая дата-заглушка 9999-12-31 |
| Очистка команды | Native SQL зависел от `search_path` | Используется Hibernate `{h-schema}` и связанный параметр команды; проверено в отдельной схеме |

Загрузка нескольких независимых коллекций отдельными запросами и JDBC batching — штатные механизмы [Hibernate](https://docs.hibernate.org/orm/6.6/userguide/html_single/). События истории используют его штатную поддержку неизменяемых сущностей. Перезапись пакетных INSERT — параметр [pgJDBC](https://jdbc.postgresql.org/documentation/use/).

Кеш сущностей и результатов планирования не добавлен: ошибки актуальности нагрузки и ревизий здесь дороже небольших справочных запросов. Списки продолжают получать страницу идентификаторов в БД, затем детали этой страницы; пагинация коллекций в памяти не вводится. Capacity и таблица сотрудников используют SQL-агрегации/проекции.

## Схема и миграция

Новые изменения находятся в отдельной миграции `1.0.0_23_redundant_task_indexes.sql`: один changeset без preconditions. Файл 22 восстановлен к исходному содержимому и checksum. Совместимость с уже применённой 22 и прежним вариантом 23, сохранность строк и повторный запуск описаны в [проверке миграции 23](migration-merge-safety.md). Java-код оптимизации не менялся.

| Удаляемый индекс | Остающийся первичный ключ |
| --- | --- |
| `idx_task_allocations_task(task_id)` | `task_allocations(task_id, participant_id, sprint_id)` |
| `idx_task_loads_task(task_id)` | `task_loads(task_id, sprint_id)` |
| `idx_task_participants_task(task_id)` | `task_participants(task_id, participant_id)` |

Поиск по `task_id` поддерживается левым префиксом составного B-tree. Это подтверждено `EXPLAIN (ANALYZE, BUFFERS)` на тестовой выборке: после удаления трёх индексов PostgreSQL использует соответствующие PK. Общее правило описано в [документации PostgreSQL 15](https://www.postgresql.org/docs/15/indexes-multicolumn.html).

Каждый `DROP INDEX CONCURRENTLY IF EXISTS` находится в отдельном changeset с `runInTransaction:false`; rollback восстанавливает индекс через `CREATE INDEX CONCURRENTLY`. Эти операции могут ожидать завершения конфликтующих транзакций; запрет на выполнение внутри транзакционного блока и ограничения CONCURRENTLY описаны в [PostgreSQL DROP INDEX](https://www.postgresql.org/docs/15/sql-dropindex.html). Три отдельных SQL-оператора выполняются в одном нетранзакционном changeset; `IF EXISTS` позволяет повторить его после частичного выполнения.

Интеграционная проверка создала случайную отдельную схему, выполнила весь changelog, откатила changeset 23, добавила задачу/участника/нагрузку, повторно применила миграцию и проверила сохранность данных и PK. Затем проверены запросы приложения при Hibernate default_schema, отличающемся от search_path. Схема удалена, число задач в public не изменилось.

Оставлены следующие внешне похожие данные:

- `task_participants` хранит назначение без нагрузки. По одним allocations такого участника восстановить нельзя.
- `task_loads` хранит самостоятельную нагрузку задач без исполнителя и суммарную нагрузку остальных задач. Удаление потребовало бы изменения контракта API и логики агрегаций.
- `tasks.customer/stream` ещё используются совместимостью API, поиском и сортировкой вместе с многозначными справочниками. Их возможное удаление — отдельное изменение с переводом читателей и миграцией, а не безопасная уборка в этой задаче.
- `planning_backlog_items` — отдельные заготовки, а не копия текущей нагрузки ROADMAP. JSONB окон/потребностей и `source_notes`, `source_leader_id`, `source_revision` сохраняют данные и проверяют актуальность при переносе. Они используются кодом.
- Уникальные пары `(id, team_key)` нужны составным внешним ключам, защищающим границы команд. Они не удалялись как якобы дубликаты PK.
- `team_key` в дочерних таблицах участвует в ограничениях принадлежности одной команде и фильтрации запросов; его удаление потребовало бы пересмотра этой защиты.
- Индексы с другим первым столбцом, частичные и уникальные индексы оставлены: они обслуживают другие условия/ограничения. Последовательное сканирование справочника из нескольких десятков строк само по себе не является ошибкой плана.

## Методика замеров

Использована отдельная PostgreSQL 15.15 `sprints_audit` в контейнере на порту 5433. Основная локальная БД не использовалась и тестовыми данными не заполнялась. API работал на 8081: один и тот же образ Java 21, 2 CPU, память 2 GiB, `-Xmx1024m`. Базовый и итоговый JAR запускались последовательно.

Фикстура: 50 активных участников, 500 задач (400 ROADMAP со статусами inprogress/done/canceled и 100 BACKLOG), от 1 до 10 участников в задаче, 2750 назначений, 16500 ячеек нагрузки, 3000 суммарных нагрузок, 4 квартала/24 спринта/24 релиза, 500 заготовок, 2600 Jira-ссылок и 20000 записей истории этой команды. Это проверка указанного объёма данных, а не оценка максимального числа одновременных пользователей.

Для чтения — 5 прогревочных запросов и 20 измерений на случай. Для записи — 2 прогревочных и 10 измерений, кроме отдельно обозначенного дорогого повторного baseline связанного применения. После каждой записи восстанавливались только строки собственной фикстуры; записи истории замера удалялись отдельно. PostgreSQL `pg_stat_statements` сбрасывался перед каждым случаем. Управляющие SQL восстановления и диагностическое чтение `pg_stat_activity` исключены из счётчиков.

За время проверки фоновая производительность локального окружения изменилась: например, неизменённая выдача трёх кварталов замедлилась примерно в четыре раза. Поэтому исходный JAR повторно измерен рядом с итоговым, на том же текущем состоянии БД, уже после удаления трёх индексов. Сравнение в таблицах отделяет эффект Java-кода от изменения индексов и фоновой скорости машины. Первоначальные замеры сохранены в `/tmp/sprints-backend-java21-before.json` и `/tmp/sprints-backend-java21-writes-before.json`; для итоговых сравнений используются повторные baseline.

Один из промежуточных прогонов был прерван автоматическим сном macOS: журнал питания подтвердил Maintenance Sleep, Hikari зарегистрировал паузы 17 и 8 минут. Такой прогон исключён. Итоговые проверки и повторный baseline выполнялись с временным `caffeinate -i`; системные настройки энергосбережения не изменялись.

Для повторного baseline `planning_apply20_linked` выполнены три измерения без дополнительного прогрева после остальных операций записи. Его эмпирический p95 в таблице равен максимуму трёх наблюдений и имеет меньшую статистическую надёжность. Первый baseline этой операции дополнительно содержит десять измерений с двумя прогревочными. У итоговой сборки во всех операциях записи десять измерений после двух прогревочных. Число наблюдений сохранено для каждой строки JSON-отчёта.

В чтении намеренно отсутствуют `X-Session-Id`/`X-User-Name`, поэтому измеряется сама выдача, без асинхронной общей истории HTTP. В записи заголовки есть: включены предметная история и завершившиеся вспомогательные записи HTTP. Политика журналирования GET в приложении не менялась.

SQL в результатах — число выполнений серверных SQL-команд, включая отдельные строковые UPDATE/DELETE. Это **не** число сетевых round trip: JDBC batch отправляет несколько таких команд пакетом. Рост DML при реальном изменении сотен ячеек не равен N+1 чтению. Медиана и p95 — локальное HTTP-время, включая JVM, сериализацию и сеть; небольшие различия чувствительны к JIT, GC и фоновой нагрузке машины.

## История и функциональные проверки

Предметная история дополнена workspace и снимками allocations/loads при создании, изменении и удалении, изменением самостоятельной нагрузки, ручными Jira-ссылками и созданием Story Jira. История задач синхронно участвует в транзакции изменения задачи; неуспешное изменение откатывается вместе с событием. Общий журнал HTTP остаётся асинхронным и может отдельно содержать запись неуспешного HTTP-вызова.

Существующее условие обычной истории задач сохранено: запрос должен передавать `X-Session-Id`; фронтенд его передаёт. Прямые запросы без этого заголовка не создают предметные события. Экспорт Jira сохраняет собственный идентификатор сессии.

Проверяются автор и сессия, before/after, отсутствие событий при неизменённых значениях, сохранение истории после удаления, переносы BACKLOG/ROADMAP, применение самостоятельных и связанных заготовок. Отдельно выполняются mock-экспорт Jira со Story и двумя задачами участников и две гонки: применение дважды; применение одновременно с удалением.

API сверены с SQL: точный состав и страницы ROADMAP/BACKLOG, все 50 участников, каждая ячейка capacity, включение всех статусов ROADMAP, исключение BACKLOG, ошибка 400 без квартала и 404 при обращении к задаче другой команды. UI-сценарии дополнительно покрывают неактивных и назначенных без нагрузки участников, старые ревизии, ручные релизы и очистку команды.

Итоговая сборка: 95 unit-тестов без ошибок. На Java 21 отдельно пройден тот же набор, после финальных изменений повторены 22 затронутых теста нагрузки, участников и Jira; два интеграционных теста без соответствующих переменных окружения пропускаются. Opt-in проверка PostgreSQL/Liquibase/JSONB отдельно пройдена на Java 21 (1 тест); таким образом выполнены 95 unit и 1 интеграционный тест. ## Повторение

1. Создать **отдельную** PostgreSQL с БД/пользователем/паролем `sprints_audit`/`audit`/`audit`, `shared_preload_libraries=pg_stat_statements`; создать расширение `pg_stat_statements`. Основную БД использовать нельзя.
2. Запустить проверяемый JAR на локальном порту 8081, направив datasource в эту БД; применить Liquibase. Для сценариев Jira обязательно `APP_JIRA_MOCK_ENABLED=true`. Контейнеры должны называться `sprints-planning-audit-db` и `sprints-planning-audit-api` и иметь label `codex.audit=sprints-backend`.
