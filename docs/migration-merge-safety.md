# Объединение и проверка миграций 22/23

8 ноября 2026. Для этих изменений остался один физический SQL-файл: [1.0.0_22_roadmap_backlog.sql](../server/database/1.0.0/1.0.0_22_roadmap_backlog.sql). Отдельный файл 23 удалён, отдельного include в changelog нет. Версии Java, Spring Boot, Liquibase и остальных зависимостей не менялись.

Внутри файла сохранены четыре changeset: транзакционный шаг 22 и три независимых удаления индексов. Объединять их в одну транзакцию нельзя: PostgreSQL запрещает `DROP INDEX CONCURRENTLY` внутри транзакционного блока. Каждая операция с индексом выполняется отдельно и имеет свой rollback. [PostgreSQL 15: DROP INDEX](https://www.postgresql.org/docs/15/sql-dropindex.html).

## Совместимость с уже применёнными миграциями

В основной локальной БД уже применена 22, в тестовой — 22 и все три шага 23. Поэтому SQL существующих changeset не переписывался. Сохранены авторы, идентификаторы и checksum:

| Changeset | Checksum |
| --- | --- |
| `1.0.0-22` | `9:ac2553200a58eb37a153e037a9be53d3` |
| `1.0.0-23-alloc-task-index` | `9:42288ef26858366c36ab3137dfea012d` |
| `1.0.0-23-load-task-index` | `9:7f3fcc216b0f663be730281635d83b4b` |
| `1.0.0-23-participant-task-index` | `9:81e2668e5a043d178e36a6983aaf0f63` |

Для перемещённых шагов 23 указан прежний `logicalFilePath`. Это идентификатор истории Liquibase, а не подключение удалённого файла. Уже выполненные шаги распознаются и повторно не запускаются. Применён стандартный механизм [Liquibase для переноса changeset](https://support.liquibase.com/hc/en-us/articles/42999734689947-Using-logicalFilePath-to-Restructure-Changelogs), проверенный на используемом Liquibase 4.29.2. `clearCheckSums`, `validCheckSum:ANY`, ручное редактирование DATABASECHANGELOG и повторное выполнение старого SQL не использовались.

## Какие данные действительно меняются

Бизнес-SQL шага 22 остался прежним:

- `notdone` заменяется на `canceled`, `partial` — на `done`, как ранее согласовано.
- Для `backlog` задаётся `workspace=BACKLOG`, для остальных существующих задач — `ROADMAP`; новая `revision` равна нулю.
- Добавляются поля связи заготовки с исходной задачей. У существующих заготовок ссылки/revision/leader остаются NULL, `source_notes` получает пустой объект; их прежние поля не переписываются.
- Добавляются ограничения целостности и уникальности дат релизов в пределах команды.

Остальные три changeset удаляют только обычные индексы по `task_id`. Остаются первичные ключи с ведущим `task_id`. Удаления задач, участников, назначений, нагрузки, релизов, истории или колонок нет. Никакого автоматического слияния релизов или переназначения ссылок не производится.

## Защитные проверки

Перед первым выполнением 22 проверяются неподдерживаемые статусы и дубли `(team_key, prom_date)`. При обнаружении миграция останавливается до ALTER/UPDATE, сохраняя данные для явного решения конфликта.

Перед удалением каждого индекса проверяются:

- Наличие валидного PK с ведущим `task_id`, который поддерживает существующие запросы.
- Принадлежность найденного индекса именно нужной таблице. Это предотвращает удаление одноимённого индекса другой схемы при `search_path` из нескольких схем.
- Ожидаемая структура: обычный неуникальный B-tree ровно по `task_id`, без INCLUDE, выражений и частичного условия. Изменённый вручную уникальный индекс не удаляется.

Отсутствующий индекс допускается: операция уже могла завершиться до записи в историю Liquibase. Допускается и невалидный обычный индекс ожидаемой структуры, оставшийся после прерывания concurrent DROP; валидность сохраняющегося PK обязательна в любом случае. Проверки PostgreSQL-каталогов выполняют только SELECT.

## Проверки на PostgreSQL и Java 21

Тесты запускаются только с `BACKEND_AUDIT_DB_URL`, указывающим на отдельную БД `sprints_audit`. Для каждого сценария создаётся собственная случайная схема; тестовая фикстура отказывается выполняться вне такой схемы. Основная локальная БД не изменялась.

Проверяется полный снимок строк всех бизнес-таблиц, включая тексты с переносами, JSONB, даты и стадии релизов, связанные справочники, Jira-ссылки, историю, активных/неактивных участников, назначения без нагрузки, allocations/loads и заготовки. При первом обновлении разрешены только перечисленные выше изменения статусов и новые поля. После уже применённой 22 сравниваются все поля, включая ненулевую revision, BACKLOG/canceled и заполненные source-поля.

Сценарии:

1. Разбор единого файла, точное совпадение четырёх checksum, идентификаторов, логических путей и границ транзакций; отсутствие старого файла в classpath.
2. Обновление заполненной схемы с версии 21; уже применённая 22; частично применённая 23; повторный запуск без изменений данных и журнала; восстановление трёх индексов rollback и повторное применение.
3. Дубликаты дат релизов с разными календарными полями и существующими ссылками: отказ без слияния, удаления или перепривязки.
4. Неизвестный статус: отказ без исправления исходных данных.
5. Искусственная поздняя ошибка CREATE INDEX после ALTER/UPDATE: вся 22 откатывается вместе с изменениями статусов и структуры.
6. Отсутствие покрывающего PK: удаление индексов не начинается.
7. Одноимённый индекс другой схемы и вручную подменённый уникальный индекс: оба сохраняются, миграция останавливается.
8. Блокирующая транзакция и локальный `lock_timeout` тестового соединения: ошибка откатывает 22 без изменения данных.
9. Настоящее прерывание `DROP INDEX CONCURRENTLY` по statement_timeout при удерживаемом чтении: оставшийся невалидный индекс затем корректно удаляется повторным запуском, строки сохраняются.
10. Чистая установка, rollback индексов и Hibernate validate в непубличной схеме — существующий `BackendSchemaAuditIntegrationTest`.

Результат: 10 новых тестов `MigrationMergeSafetyTest` и один существующий интеграционный тест прошли на Java 21/PostgreSQL, без ошибок. Новый запуск Liquibase в тесте использует новое соединение и очищает только внутрипроцессный FastCheck-кэш, как в новом JVM; checksum и записи журнала при этом не сбрасываются.

Собранный JAR дополнительно запущен на отдельном порту против тестовой БД, в которой старые 22/23 уже применены. Файл 23 отсутствует в JAR, но прежние записи истории распознаны. Отпечатки всех 21 таблицы, включая DATABASECHANGELOG, до и после запуска совпали. API вернул прежние 400 ROADMAP-задач, 100 BACKLOG-задач и 500 заготовок. Временный проверочный сервер удалён; исходные локальные сервисы не заменялись.

Все восемь preconditions отдельно выполнены в основной локальной БД внутри READ ONLY-транзакции и прошли. Сама миграция там не запускалась. Машиночитаемый результат: [migration-merge-results.json](migration-merge-results.json).

Команда для повторения после компиляции тестов:

```sh
BACKEND_AUDIT_DB_URL=jdbc:postgresql://localhost:5433/sprints_audit \
  mvn -Drevision=0.1.0 -Dtest=MigrationMergeSafetyTest,BackendSchemaAuditIntegrationTest test
```

## Границы безопасности

Абсолютной гарантии для произвольного состояния БД и параллельного административного DDL нет. ALTER TABLE и создание ограничений/уникальных индексов в 22 берут обычные PostgreSQL-блокировки; concurrent DROP может ожидать старые транзакции. Добавленные preconditions не делают эти операции полностью свободными от блокировок. `lock_timeout` в тесте задаётся только тестовому соединению, а не скрыто меняет настройки приложения.

Автоматический rollback проверен для трёх шагов очистки индексов. Полный автоматический rollback бизнес-шага 22 не объявлялся: после замены partial → done исходные статусы нельзя однозначно восстановить из новых данных. Отказ внутри 22, напротив, транзакционно возвращает её исходное состояние.
