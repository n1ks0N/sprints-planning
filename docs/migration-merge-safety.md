# Безопасность отдельной миграции 23

8 ноября 2026. Новые изменения вынесены в [1.0.0_23_redundant_task_indexes.sql](../server/database/1.0.0/1.0.0_23_redundant_task_indexes.sql), подключённый после 22 в changelog. Файл 22 полностью восстановлен из исходного коммита `765a899`; его SQL, идентификатор и checksum `9:ac2553200a58eb37a153e037a9be53d3` не изменены.

## Что выполняет 23

Один changeset `sprints:1.0.0-23`, без preconditions и вспомогательных SELECT. Он выполняет три `DROP INDEX CONCURRENTLY IF EXISTS`:

| Удаляемый неуникальный индекс | Остающийся первичный ключ |
| --- | --- |
| `idx_task_allocations_task(task_id)` | `task_allocations(task_id, participant_id, sprint_id)` |
| `idx_task_loads_task(task_id)` | `task_loads(task_id, sprint_id)` |
| `idx_task_participants_task(task_id)` | `task_participants(task_id, participant_id)` |

Строки таблиц, колонки, внешние ключи и ограничения уникальности не меняются. Остающиеся B-tree индексы первичных ключей обслуживают поиск по первому столбцу `task_id`. Определения трёх удаляемых индексов и трёх PK дополнительно проверены READ ONLY-запросом в основной локальной БД; миграция там не запускалась.

`runInTransaction:false` нужен для CONCURRENTLY. Liquibase исполняет три SQL-оператора последовательно вне транзакции. Если процесс прервётся после части операций, повторный запуск завершит оставшиеся благодаря `IF EXISTS`; это проверено и для индекса, оставшегося невалидным после отменённого concurrent DROP. Имена объектов обычные, без подстановок Liquibase, как в остальных SQL-файлах проекта.

Rollback одного нового changeset восстанавливает три обычных индекса через `CREATE INDEX CONCURRENTLY IF NOT EXISTS`. Rollback не меняет строки таблиц и не затрагивает миграцию 22.

## Ручной запуск SQL

Файл можно запускать обычным SQL-скриптом: все строки Liquibase и rollback являются комментариями для PostgreSQL. Подстановок `${...}` в нём нет. Выберите целевую схему через настройки подключения/search_path, как при выполнении предыдущих миграций; целевая схема должна быть единственной схемой приложения в search_path.

`DROP INDEX CONCURRENTLY` требует autocommit и отдельного выполнения каждого оператора, без BEGIN/COMMIT. При выполнении скрипта клиент должен отправлять SQL-операторы последовательно, как `psql -f`. Передача всех трёх команд одним пакетным SQL-запросом создаёт транзакционный блок и для CONCURRENTLY не подходит. Комментарий `runInTransaction:false` управляет только Liquibase и не настраивает SQL-клиент.

## Уже применённые версии

На БД с применённой 22 Liquibase выполняет только новую 23. Если прежний вариант из трёх шагов `1.0.0-23-*-task-index` уже применялся частично или полностью, его записи остаются в DATABASECHANGELOG без изменений. Новая 23 имеет отдельный идентификатор и безопасно пропускает отсутствующие индексы. Записи истории, checksum старых шагов и `clearCheckSums` вручную не меняются.

## Проверки

`MigrationSafetyTest` проверяет исходный checksum 22, один changeset в отдельном файле 23 и отсутствие preconditions. PostgreSQL-сценарии сравнивают полный JSON-снимок всех бизнес-таблиц до/после, проверяют повторный запуск, rollback/reapply, сохранность первичных ключей, прежнюю историю 23 после 0/1/3 шагов, прямое выполнение SQL без Liquibase и отмену concurrent DROP.

Также сохранены проверки атомарности исходной 22 при дублирующихся датах релизов, неизвестном статусе, конфликте DDL и lock timeout. Без preconditions ошибку отклоняют обычные ограничения БД, а транзакция 22 откатывается целиком. Миграция 23 не добавляет преобразований данных к уже существующей 22.

Все 11 сценариев миграции и проверка отдельной схемы прошли на Java 21/PostgreSQL 15. Полный набор бэкенда: 107 успешных тестов, один необязательный пропущен. Результаты прогона: [migration-merge-results.json](migration-merge-results.json). Проверка запуска Spring/Hibernate и работы запросов в непубличной схеме — `BackendSchemaAuditIntegrationTest`.

Для предыдущего варианта `609bde5` отдельно собран JAR и запущен на отдельной БД с уже применёнными 22 и старой 23, 50 участниками и 500 задачами. Снимки всех 20 бизнес-таблиц и прежние записи DATABASECHANGELOG совпали до/после; добавилась ровно одна запись нового changeset 23. API вернул 400 ROADMAP, 100 BACKLOG и 500 planning-заготовок. В проверенном JAR присутствуют отдельные 22/23, тестовые SQL-фикстуры отсутствуют. После удаления подстановки текущий SQL-файл дополнительно дважды выполнен напрямую через `psql -f` без Liquibase: строки и три первичных ключа сохранились.

CONCURRENTLY допускает обычные чтения и записи, но может ожидать завершения старых транзакций. Исходная 22 по-прежнему выполняет свои прежние изменения статусов и DDL с обычными блокировками; это содержимое не является частью нового changeset 23. Версии Java, Spring Boot, Liquibase и ORTools не менялись.
