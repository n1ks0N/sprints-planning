# Главная: цепочка запросов и рендеров

## Первопричины

На странице было три владельца справочника релизов: список дат для назначения в карточке, список для расшифровки истории и собственный запрос компонента фильтра. Два последних запрашивали одинаковые данные, но аргументы RTK Query отличались: `search: ""` и отсутствие `search` создавали разные ключи кэша, хотя HTTP-запросы совпадали.

При пустом localStorage текущий квартал устанавливался эффектом уже после первого рендера. До этого успевали уйти два запроса релизов без ограничения кварталом и запрос задач без квартала. После загрузки справочника эффект менял фильтр, и запросы повторялись. `StrictMode` не был первопричиной и остался включённым.

Дополнительно санитизация фильтров каждый раз создавала новые массивы для всех полей. Это меняло ссылки даже у неизменённых параметров, мешало мемоизации и запускало лишнюю работу дочерних компонентов. Начальное состояние формы создания и порядок участников также копировались в состояние всей страницы через эффекты.

## Изменения

- `useResolvedQuarterFilter` разрешает начальные и невалидные сохранённые кварталы до первого зависимого запроса; эффект сохраняет уже использованный набор, не меняя сетевой контекст. До загрузки кварталов задачи и релизы не запрашиваются. Для ошибки справочника есть повторная загрузка. Механизм общий для задач и планирования.
- Фильтр — единственный владелец начального запроса релизов выбранных кварталов. Список для назначения загружается при открытии поля; запрос и состояние загрузки находятся в самом поле. Открытие другого поля использует общий кэш. После закрытия поля активная подписка снимается.
- Планирование также не загружает справочник для редактора до открытия редактора. Даты в списке берутся из DTO заготовок, а не из дополнительного справочника. Удалена повторная установка всех локальных фильтров при монтировании уже инициализированной страницы.
- История монтируется только при открытии и разрешает только ID релизов из своих изменений. Это сохраняет подписи исторических дат за пределами текущих кварталов.
- Аргументы релизов канонизируются одинаково для URL и кэша: пустые параметры исключаются, ID сортируются и дедуплицируются. При поиске не включаются ограничения кварталами/датой, которые сервер и так игнорирует; при запросе по ID остаются только ID и команда.
- Фильтры сохраняют ссылки на неизменённые массивы; повторное применение того же состояния не меняет Redux. Общие фильтры мемоизированы. Пустые массивы справочников стабильны, преобразования кварталов мемоизированы.
- Состояние квартала создания отделено от состояния страницы. Его изменение не рендерит страницу, фильтры или список задач. Порядок участников по умолчанию берётся непосредственно из задачи; локальная копия нужна только при пользовательском изменении.
- Тяжёлые страницы мемоизированы относительно родителя. Подписки на справочники выбирают используемые данные без ненужных флагов запросов. `pinnedTaskId` читается при инициализации состояния, а не устанавливается после первого запроса эффектом.

Изменений SQL, миграций и контрактов серверных API не потребовалось. Снижается количество обращений к уже существующим запросам сервера; полные справочники вместо ограниченных выборок не загружаются.

## Замеры и проверки

Локальная development-сборка, `StrictMode` включён, команда `customlab`, замер до ввода поиска:

| Сценарий | Запрос | До | После |
| --- | --- | ---: | ---: |
| Пустой localStorage | `/releases/options` | 5 | 1 |
| Пустой localStorage | `/tasks` | 2 | 1 |
| Пустой localStorage | Все начальные GET | 13 | 8 |
| Сохранённый квартал | `/releases/options` | 3 | 1 |
| Сохранённый квартал | `/tasks` | 1 | 1 |
| Сохранённый квартал | Все начальные GET | 10 | 8 |

`/quarters/options` — отдельный справочник кварталов, один начальный запрос. Это другой ресурс, а не дубль `/releases/options`.

Браузерные регрессионные проверки с реальным API подтверждают:

- С замедленным ответом справочника кварталов нет промежуточных запросов без квартала; после разрешения фильтров — ровно один запрос релизов и один запрос задач.
- Изменение квартала создания не обновляет `BacklogPage`, `TaskCardsList`, `QuarterFilter` и `ReleaseFilter`.
- Ввод поиска релиза не обновляет страницу, список карточек и фильтр кварталов и не перечитывает задачи. Возврат к пустому поиску использует кэш.
- Каталог будущих релизов запрашивается при первом открытии назначения и используется повторно другой карточкой без нового HTTP-запроса.
- Планирование начинает загрузку с разрешённым кварталом, показывает дату из DTO и загружает справочник редактора только при его открытии.
- Запрос ID исторических релизов отсутствует до открытия истории; после открытия выполняется один запрос нужных ID.

Счётчики React устанавливаются только в браузерных тестах через development renderer hook; инструментирования и счётчиков в production-коде нет. Старый формат фильтра с ID релиза вне текущих подсказок может потребовать отдельного запроса ID для восстановления даты; это загрузка отсутствующих данных, а не повтор одинакового запроса.

Этот документ описывает оптимизацию первоначальной загрузки и общих фильтров. Последующее расширенное ревью страниц, хуков, таблиц, кэширования и production-сборки, включая актуальный набор проверок, описано отдельно в [аудите фронтенда](frontend-performance-audit.md).
