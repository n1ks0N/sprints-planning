# Аудит производительности фронтенда

Проверены страницы дорожной карты, бэклога, планирования и review, нагрузки, сотрудников, участников, кварталов/спринтов, релизов, истории и выбора команд; общие фильтры, редакторы ячеек, контексты и RTK Query. Предыдущее [ревью начальных запросов](api-render-performance-review.md) охватывало более узкую цепочку загрузки главной страницы.

## Кнопка планирования

В бэклоге действие переключается между «Добавить в планирование» и «Убрать из планирования», аналогично корзине Jira. Во время добавления повторный запрос блокируется. Удаление снимает выбор из текущего набора, сохраняя серверную заготовку; повторное добавление возвращает ту же заготовку. Выбор сохраняется при навигации внутри команды, смена команды сбрасывает его. Отменённую выбранную задачу можно убрать, добавить отменённую нельзя.

Единственный источник признака выбора — `PlanningSelectionContext`. Удалено отдельное локальное состояние «успешно добавлена», которое могло расходиться с текущим набором. Обычный `useReducer` одновременно обновляет выбор и кеш элементов; обработчики стабильны, операции без изменений возвращают прежнее состояние.

## Найденные причины и изменения

| Область | Причина лишней работы | Реализация |
| --- | --- | --- |
| Дорожная карта и бэклог | Новые массивы кварталов, строк участников и итогов на каждый рендер; дублирование нагрузки в локальном состоянии | Мемоизированы вычисления и значения фильтров. Нагрузка читается прямо из RTK Query; удалён эффект её копирования после первого отображения карточек. Оптимистические обновления и откаты выполняет существующий lifecycle мутаций |
| Ячейки нагрузки | Inline-обработчики меняли props каждой соседней ячейки | Общий `TaskAllocationCell` с `React.memo`, примитивными ID и стабильными `useCallback`; черновой ввод остаётся внутри редактора |
| Сотрудники | Синхронизация нагрузки всегда помечала состояние изменённым; начальный квартал устанавливался эффектом после загрузки | Исправлены проверка изменений и сохранение ссылок; начальный квартал разрешается до запросов. Серверная пагинация и обновление загруженного префикса сохранены |
| Нагрузка и кварталы/спринты | Каскад эффектов и промежуточный запрос без квартала | Общий `useResolvedQuarterFilter`, стабильные пустые справочники и подписки на используемые данные. Явная очистка фильтра означает все кварталы |
| Планирование | Поиск обновлял всю страницу на каждую букву; свежие данные перечитывались при каждом возврате | Локальный ввод в общем поле поиска, debounce 250 мс, очистка таймера, применение по blur/Enter. RTK Query использует свежий результат в течение 30 секунд; инвалидации, focus и reconnect сохраняют актуальность |
| Review | `structuredClone` всей сетки при изменении одной ячейки/строки, повторный обход items при apply | Копируются только изменённые ветки состояния. Повторная запись того же значения возвращает прежнее состояние. При apply используется один `Map` по ID |
| Участники | Ввод в форме создания или редактирования находился в состоянии всей страницы | Черновики перенесены в форму и отдельную мемоизированную строку. В родителе остаётся ID редактируемой строки, одна строка редактируется за раз. DnD и CRUD сохранены |
| История | После смены страницы в `data` временно оставалась предыдущая страница и добавлялась снова | Используется `currentData`, объединение по `sessionId`, без повторов при focus/refetch |
| RTK Query | Разный порядок одинаковых значений фильтра создавал разные записи кеша или принудительное перечитывание | Общая канонизация ключей существующих endpoint: сортировка и дедупликация множеств, исключение пустых параметров; одинаковый ключ используется в пагинации и чтении кеша. `forceRefetch` не перечитывает тот же набор фильтров из-за другого порядка значений |
| Обновление RTK Query | `refetchOnFocus`/`refetchOnReconnect` были указаны, но `setupListeners` отсутствовал | Подключён стандартный `setupListeners(store.dispatch)`. Polling Jira останавливается у неактивной вкладки; прежние условия открытого диалога и незавершённого задания сохранены |
| Контексты и справочники | Нестабильные функции и создание нового пустого состояния даже без изменений | Стабильные callbacks корзины Jira и планирования; no-op операции сохраняют ссылки. `useActiveParticipantsQuery` выбирает данные и мемоизирует активных участников |
| Общий Autocomplete | Хуки одиночного и множественного режима вызывались после условной ветки | Режимы разделены на два обычных компонента с безусловным порядком хуков и общей нормализацией options |
| Оболочка и страницы | Изменения Header проходили в тяжёлые страницы; все страницы загружались сразу | `React.memo` на границах страниц и тяжёлой таблицы, `React.lazy`/`Suspense` для маршрутов. Загрузка новой страницы сохраняет Header |
| Production JS | Moment автоматически включал весь каталог локалей | Стандартный webpack `IgnorePlugin`; явный импорт русской локали сохранён |
| Смена квартала | Старые задачи из `data` получали новый набор спринтов до ответа API; `startTransition` вокруг Redux создавал дополнительные pending-рендеры | Используется `currentData`; удалены эти обёртки. Общая мемоизированная граница списка использует `useDeferredValue` для согласованной прерываемой отрисовки данных, колонок и обработчиков |
| Длинный список карточек | Однократный монтаж всех карточек с MUI-полями и таблицами всё равно блокировал поток | TanStack Virtual отображает видимую область с запасом в одну карточку. Динамическая высота измеряется библиотекой, редактируемая и перетаскиваемая карточки сохраняются в DOM. Для списков до четырёх карточек оставлен обычный вывод |
| DnD списка | Новые options сенсоров, массив ID и объект dragHandle меняли контекст и props карточек | Стабилизированы параметры сенсоров, ID и dragHandle. Команды читают актуальную страницу через стандартный selector RTK Query в момент действия |

Страницы релизов и выбора команд также проверены: их локальное состояние и текущая модель запросов сохранены, добавлены мемоизация границы страницы и загрузка по маршруту. Формы и редакторы не заменялись новой архитектурой.

## Проверка

- `npm run typecheck`, `npm run build`, `git diff --check`.
- Playwright: 21 сценарий с моками и 29 с реальным API/PostgreSQL, `StrictMode` включён.
- В тестовой сетке из восьми ячеек черновой ввод не обновляет обёртки ячеек; сохранение одной ячейки не обновляет остальные семь, включая ячейки той же задачи.
- Ввод в форме участника не обновляет страницу и соседние строки; создание, сохранение и деактивация проверены реальным API.
- Поиск квартала не обновляет таблицу нагрузки. Перестановка уже выбранных кварталов использует ту же запись RTK Query без нового запроса.
- Поиск планирования не обновляет страницу на каждый символ; после паузы выполняется один запрос. Возврат к исходному поиску использует кеш.
- Пагинация истории и обновление по focus не создают дубли. Начальная загрузка нагрузки выполняет один запрос с разрешённым кварталом.
- Добавление, удаление из выбора и повторное добавление в планирование проверены в браузере; существующая серверная заготовка не удаляется.
- Добавлены сценарии с 20 тяжёлыми карточками: смена квартала на обеих страницах, отсутствие первого отображения без нагрузки и повторного монтажа видимых карточек, сохранение черновика при прокрутке, измерение высоты, серверная догрузка, drag-and-drop, изоляция изменения одной карточки и откат API-ошибки. Отдельно проверены копирование нагрузки в следующий квартал и сдвиги строки/всей задачи.

Начальная проверка локального ввода не измеряла смену квартала на длинном списке. Последующая жалоба на задержку воспроизвелась: прежних проверок было недостаточно для вывода о скорости этой цепочки. Условия и отдельные замеры приведены в [проверке смены квартала](quarter-render-performance.md).

Счётчики рендеров устанавливаются только тестами через development renderer hook. В production нет счётчиков, дополнительных подписок или собственного профилировщика.

## Production-сборка

Сравнивается сохранённая сборка до оптимизации с новой сборкой: свежий браузерный контекст, одна команда и одна задача дорожной карты, загрузка до показа карточки и завершения начальных сетевых запросов. Считается размер действительно загруженных минифицированных JS-файлов без gzip. Проверка новой сборки также открывает страницу релизов, подтверждает загрузку её чанка по требованию и отсутствие ошибок JavaScript.

| Метрика | До | После |
| --- | ---: | ---: |
| Начальный JS, байт без сжатия | 1 222 739 | 918 387 |
| Крупнейший vendor-чанк | 931 KiB | 502 KiB |
| Код ещё не открытых страниц | Загружается заранее | Загружается при переходе |

Начальный объём JS снизился примерно на 25%. Это измерение объёма, а не обещание такого же снижения времени открытия: задержки сети, данные и устройство влияют на фактическую скорость. Webpack по-прежнему сообщает о размере крупного vendor-чанка.

После добавления виртуализации начальный JS вырос с 876 114 до 918 387 байт относительно первого этапа аудита (около 42 КБ). Это стоимость стандартной библиотеки, устраняющей монтаж длинного списка; относительно первоначальной сборки начальная загрузка остаётся меньше примерно на 25%.

## Принципы и границы

Используются стандартные средства React и RTK Query: локальное состояние, `useReducer`, `useMemo`, `useCallback`, `React.memo`, `selectFromResult`, `serializeQueryArgs`, `setupListeners`, `React.lazy`, `Suspense` и `useDeferredValue`. Хуки применяются там, где сохраняют полезную ссылку или изолируют измеренную работу. `useDeferredValue` добавлен после измерения тяжёлой смены списка; `startTransition` вокруг внешнего Redux-хранилища удалён, поскольку он не делает изменение хранилища неблокирующим. Основание — [документация React](https://react.dev/reference/react/useSyncExternalStore#caveats).

Нет глубоких пользовательских сравнений props, callback-ref обходов зависимостей, собственной системы кеширования или новой библиотеки состояния. Серверная пагинация сохранена. Для виртуализации добавлен `@tanstack/react-virtual`; используются стандартные [оконный скроллер](https://tanstack.com/virtual/latest/docs/framework/react/examples/window) и измерение динамической высоты. SQL и API в рамках этого аудита не менялись. Это ревью основных пользовательских цепочек с регрессионными проверками; оно не является нагрузочным испытанием на произвольном объёме данных.
